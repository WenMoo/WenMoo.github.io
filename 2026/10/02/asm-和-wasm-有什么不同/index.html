学习 asm / wasm 以及在 cocos 中的使用

Author: WenMo Date: October 2, 2026  21:58:43

之前听项目组说淘宝小游戏加上了 Wasm。我们打包时通常也会同时打出 asm.js 和 Wasm。那为什么还要 asm.js，它和 Wasm 又有什么区别？这里整理一下。

一、asm.js

是什么

asm.js 是 JavaScript 的一个高度受限的子集，本身仍是纯文本的 JavaScript。它用严格的语法拿掉动态类型，计算用的内存也不走 JS 的垃圾回收，而是放在一块类型化数组里。浏览器校验通过后，可以把这段代码提前编译成机器码。

它和 TypeScript 的方向相反。TypeScript 是 JavaScript 的超集，多了类型、接口、泛型这些语法。浏览器不认识 TypeScript，要先编译，把类型擦掉，产出的仍是普通 JS。类型只在编写和编译时帮人检查错误，跑起来还是动态类型，不会因为标了 number 就变成 asm.js 那种可以提前编译的子集。

asm.js 缩小了能跑的语言，是为了让程序跑得更快。TypeScript 扩大了能写的语言，是为了让人写得更稳。

为什么

JavaScript 是动态类型，并且有垃圾回收。引擎执行时要判断这次运算的类型，还要管理对象内存，计算一密集就容易成为瓶颈。3D、音频解码、物理、大量骨骼动画都属于这种计算。

asm.js 把类型提前定死，让引擎不必每次猜测，从而把这类计算从普通 JS 里拆出来。

怎么做

asm.js 只用整数和浮点数。整数常写成 x | 0，浮点数常写成 +x。字符串、布尔值和对象都不是它的类型，相关数据以数值形式放在一块连续的 ArrayBuffer 里，通过 TypedArray 读写。

这块内存有固定大小，分配和释放由模块自己管理，不走 JS 的垃圾回收。没有类型变化，也没有这段计算带来的 GC 停顿，引擎就可以对它做提前编译。

如何编写

asm.js 可以用 JavaScript 手写，但可读性很差。它的用途是把 C/C++ 这类静态类型、手动管理内存的程序搬到浏览器上。常见做法是用 C/C++ 编写，再用 Emscripten 一类编译器编成 asm.js。

二、和 Wasm 的区别

asm.js 和 Wasm 常常是同一份 C/C++ 的两种编译结果，计算的是同一件事，跑法不同。

asm.js 生成的是 JavaScript 文本。文件大，宿主要先当脚本解析，再编译成机器码。它是合法的 JavaScript，所以只要容器能跑 JS 就能执行，只是快慢不同。

Wasm 生成的是二进制指令。宿主不把它当脚本来解析，必须实现 WebAssembly：校验、编译、分配线性内存，再和 JS 对接。体积更小，解码更快，运算更接近机器码。宿主没有这个接口时，.wasm 无法执行。

同一份计算，公开测试里 Wasm 的运行速度大约是 asm.js 的 1.3 倍；asm.js 已经充分优化之后，差距有时只剩几个百分点。解析和启动的差距更大。整局游戏的帧率不会按这个倍数上涨，因为收益只落在进了这份原生模块的计算上。

三、在 Cocos 小游戏里怎么用

构建面板里的「原生代码打包模式」可以选择 Wasm、AsmJS，或两份都打。它处理的不是我们写的 TypeScript 脚本。脚本依然是普通 JavaScript。

被这条选项影响的是引擎里用 C/C++ 写的模块，例如 Spine、物理（Bullet、PhysX、Box2D），以及 WebGPU。小游戏容器都能跑 JavaScript，较新的容器才提供 WebAssembly，所以这些模块要用 Emscripten 编成 asm.js 或 Wasm。

选择发生在模块加载时，不是每次播放动画时。两份都打进包里的情况下，引擎启动时看宿主有没有 WebAssembly：有就加载 .wasm，没有就退回 asm.js。之后的骨骼动画、刚体碰撞都进已经载入的那一份里计算，画到屏幕上仍由 Cocos 的渲染器完成。

淘宝容器补上 Wasm 之后，大量 Spine 动画会走这份更快的计算。动画数量多、骨骼和物理占帧时间明显时，差别更容易看出来。画面和业务脚本仍走原来的路径，整包帧率的提升通常会小于模块本身的加速。

需要注意的是，当前 cocos 引擎擎选路在 shouldUseWasmModule()：both 时看 sys.hasFeature(Feature.WASM)。小游戏里这个探测只认微信的 WXWebAssembly 和抖音的 TTWebAssembly，支付宝直接返回 false 是没有原生支持的，我们可以在 game.ejs 中做处理，修改探测的返回值，然后接入容器中的 wasm 命名指向。
