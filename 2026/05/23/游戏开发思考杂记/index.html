游戏开发思考杂记

Author: WenMo Date: May 23, 2026  21:21:39

记录杂七杂八，有些时候的一些问题和想法

2026/03/12

问：

经常修改，添加功能中，会遇到函数执行冲突的问题，是否函数应该都确保有返回，有执行结果的处理，也就是异步呢？通过异步，就能通过 await 来调整执行顺序，执行结果

答：

其实这里的关键不是“都改成异步”就能避免冲突，有点一刀切了，这里的核心是： 函数必须有明确契约（输入，输出，变化，失败处理等）

结论而言：

  • 函数不一定都要 async。纯计算/同步状态更新，保持同步更清晰。
  • 函数最好都有“可预期结果”。这个结果可以是返回值、错误、或状态对象，不一定非得 Promise。
    • 真正导致“执行冲突”的常见原因是：
    • 共享状态并发修改
    • 重复触发（重入）
    • 异步回调顺序不确定
    • 缺少取消/过期判断

2026/04/06

问：

对于不需要展示的节点，有几种方式，设置active为fasle，或者设置透明度为0，以及removeFromParent，需要再移入，或者 destroy()，这几种有什么区别呢，那种方式优化性能？

答：

方式一：其实我们日常中，应该最常见就是直接把节点 node.active = false ，实际这也是最优的，对于节点和子节点，将不参与渲染，不执行update / schedule / tween等，同时优化 CPU + GPU，CPU逻辑不跑了，GPU也不渲染了，特点是只是“关闭”，节点还是在内存的，通过active = true 可以快速恢复。在界面隐藏，页面切换等场景是非常合适的

方式二：而透明度，其实是没有性能的优化的，对于节点，依然是参与渲染，不执行update / schedule / tween等，CPU逻辑照样跑，GPU也照样渲染，场景仅仅合适做过渡效果的动画等。

方式三：而 removeFromParent 和方式一其实基本一致，不同在于再次需要的时候 addChild，而 destroy 的话，会将节点彻底销毁，内存等待CG回收，再次使用时需要重新实例的，也是最消耗性能的

这里再说一下active = false和removeFromParent，之类其实最明显的是，后者会导致节点树发生变化。也就是涉及一个关键“重绘”了，对于前者，其实是不影响的，仅仅是跳过当前节点不提交渲染，父节点基本不会重建渲染数据，对于合批，节点树都不会有影响，而后者，发生了节点树的变化，可能合批打断，DC重新计算。所以往往仅仅是长时间不使用，或者需要更换父节点才会使用 removeFromParent，不然 active = false 永远是你的第一选项~

补充： 上面说的是 cocos ，而不同的版本会有差异，在 cocos creator 3.8.2中 ui-renderer.ts 可以发现 _canRender() 中，判断了透明度为 0 的话，不参与渲染的！！！！如果说透明度为 0 不参与渲染的话，使用透明度处理可能会更好，因为不会改变渲染数据

另外再补充一种方式，那就是使用不同的相机来切换渲染场景，比如我们二合类游戏往往一个地图主界面和棋盘界面，这里如果使用两个相机，也能不影响渲染数据的改变，但该方式再cocos creator 3.x以上好像反而不好使~得一句实际场景和效果来确定

2026/05/11

问：

为什么游戏的UI树要尽可能结构简单

答：

本质而言，UI 树就是一棵“每帧都会被遍历+计算+提交”的数据结构。

首先是每帧引擎都在干什么，首先会遍历节点树，然后更新 transform，过来处理组件，收集渲染数据，处理合批，提交GPU

在遍历节点树这里，因为是链式传递，如果一个节点顺序a-b-c-d，那么如果a发生了变化，b,c,d 节点也是需要重新计算的，这里也就是脏标记的传播成本很高，当自身节点标记脏节点，那么所有子节点也都脏标记了。

这是减少结构层级最主要的问题，尽量去扁平化处理

2026/05/21

问：

了解循环引用

这里想去了解的是模块的循环引用，而不是对象的循环引用，实际上项目中也很常会碰到，比如A.ts 引用到 B.ts，而 B.ts 又引用到 A.ts。大多数情况下是不影响使用执行的，主要是不可控！可能导致重复初始化，顺序不稳定，或者一些偶现问题

可能得一些问题和实践：

答：

解决的方式，核心在于“依赖必须单向流动，不能成环”

  1. 可以A 和 B 不直接互相依赖，而是都依赖 C
  2. 改为接口的方式，不依赖具体实现，只依赖接口，比如 A.ts import IB.ts 而不是直接 import B.ts
  3. 改为 require 而不是 import
