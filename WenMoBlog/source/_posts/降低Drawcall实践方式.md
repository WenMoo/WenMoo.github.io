说到本质上，想要降低 DC ，主要就是避免合批被打断，我们 UI 树中，往往就是因为一些 Label / 不同图集 / spine / Mask 等因素而导致没法合批，再过来是一些没必要的内容导致提交渲染，下面说说一些真实实践。


## 一、UI 树顺序的调整

上面一开始我们说到合批被各种因素打断，那么调整节点位置不就可以了！UI 布局中，我们尽量是将同一个图集的内容放到相邻，而对于 Label ，我们可以都放到一个节点下，尽量避免 Label 导致的合批打断。

这里其实 cocos creator 有个插件叫 cocos Inspector 可以查看节点 DC 非常便捷好用，我们可以查看哪里导致的打断去调整。

## 二、使用 BMF 字体

上面我们知道， Label 经常是导致合批被打断，其实像奖励用的数字，进度条的数字这一类，我们可以使用 BMF 字体，本质就是使用图集，在这类基本只有数字0-9以及几个单位的情况下，也能带来不少的降低。打包字体的话有个网页工具
[snowb](https://snowb.org/) 很好用

## 三、手动分层处理

其实这种方式在刚开始看到项目中用的不少，比如我们背包格子中，每个格子有icon，数字，装饰等，一个格子占3个DC，那么我们如果是个10*10的背包，那不是最坏的情况下有300个DC？但其实我们可以对这个背包做分层，icon 一层，label 一层，装饰一层，我们把所有的 icon 都放到一层中，那么所有的 icon 在一层中都能合批，结果就会只占 1 个DC，而如果这里字体我们再用上 BMF ，那么也能只占用 1 个DC，装饰层也是类似的，那么实际下来，无论多大的背包，都会只占用 3 个DC，是不是很美妙~

但其实有个缺点，因为分层了，我们原本想要对某个格子做处理，但是实际上，我们的 UI 树下，他们都不是在一起的，会很难获取。当然我们上面列举的简单，只是一个三层的。当逻辑复杂取来，其实它不能作为一个去处理就会将逻辑变得复杂，修改调整都比较麻烦！


## 四、修改渲染数据的提交顺序

其实针对上面手动分层的问题，这里就有个很好的方式去解决，在 cocos creator 中，渲染数据的提交，遍历节点树，默认方式是深度优先的，这是合理的，这样保证了提交的渲染数据是和 UI 树上的层级一样的。但是对于列表，背包这些场景，重复的 Item 结构，其实我们可以从深度优先修改为广度优先，这样所有 Item 的渲染的时候，相同层级的就会一起提交。我记得在 cocos creator 最新的版本中，好像是加了一个属性 sort 的属性可以直接实现上述的功能。


## 五、隐藏不需要的节点

其实这个很简单，比如我们一个滑动的列表很多节点，往往我们使用虚拟列表去优化，但一些情况下，我们不方便使用，我们可以对屏幕外的节点将他的透明度调整为 0 ，或者 active 设置为 false ，都是能让这部分不参与渲染，那么 DC 自然就下来了~

需要注意，调整透明度的话，可能不同的 cocos 版本会有差异，实际可以根据项目使用版本去验证，相比设置 active 个人会更支持透明度，因为这样可以保持节点原本逻辑的继续执行，开销也没有 active 大。

## 六、使用截屏

截屏是什么意思呢？当我们打开一个弹窗的时候，弹窗底部的内容是不是还在参与渲染，这就导致我们打开的页面越多，DC 是不是就越高，但实际上，弹窗下面的东西我们是不需要操作的。那么如果我们截图放在弹窗底部做展示，而实际上我们将弹窗之下的内容全部隐藏，也就是第五点说到的，那么 DC 是不是一下子就下来了~

原理其实也很简单，我们通过摄像机截取当前的场景，然后创建一个sprite，将截取到的 SpriteFrame 设置上去，然后我们对底部的所有节点透明度调为 0，让其不参与渲染就行了，而其实这个功能我们可以封装到弹窗系统中，这样就很方便。

## 七、使用不同的摄像机

这种方式我也没实际用过，听公司大佬提到的，我们如果有一个地图的界面，以及一个战斗的玩法界面，其实是可以通过切换不同的摄像机来做切换，而这两个主界面都是使用不同的摄像机去渲染，我们就不用通过上面设置透明度或者active的方式去隐藏不需要展示部分了~


## 小结

大体上用到过的有上面的方式，当然肯定还有不少更好的方式，以后遇到继续补充~
